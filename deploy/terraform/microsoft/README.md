# Microsoft setup

Registers the Entra application mailroom links Outlook and Microsoft 365 mailboxes through —
the registration, its redirect URI, the five delegated Graph permissions, and optionally the
client secret. Under a minute, and unlike the Google side there is no manual step afterwards.

```sh
az login
terraform init
terraform apply \
  -var tenant_id=<your-tenant> \
  -var public_url=https://mail.example.com
```

Then set the two values it prints on mailroom:

```sh
MAILROOM_MICROSOFT_CLIENT_ID=<client_id>
MAILROOM_MICROSOFT_CLIENT_SECRET=<terraform output -raw client_secret>
```

An app registration is free. It is not an Azure subscription and nothing here bills.

## You need a directory, and a personal account does not have one

Every personal Microsoft account belongs to `9188040d-6c67-4c5b-b112-36a304b66dad`,
Microsoft's shared consumer directory. Registrations cannot be created there, and the way you
find out is unhelpful:

```console
$ az login --allow-no-subscriptions
[]
$ az account show
ERROR: Please run 'az login' to setup account.
```

The sign-in succeeded. There was simply no directory it could give you a session for, so
nothing was stored. `tenant_id` is required here rather than inferred for exactly this
reason — the provider's fallback is that directory, and it is never the answer you wanted.

Check what you actually have:

```sh
az account list --query "[].{tenant:tenantId,domain:tenantDefaultDomain}" -o table
```

Nothing listed means you need a directory, which is free and needs no subscription or card:
**portal.azure.com → Microsoft Entra ID → Manage tenants → Create**. Pick the country
carefully — it fixes the directory's data residency permanently. Then sign in against it:

```sh
az login --use-device-code --allow-no-subscriptions --tenant <something>.onmicrosoft.com
```

The directory is only a home for the registration. It does not have to be related to the
mailbox you are linking: a registration made here with the default audience is consented to
by an ordinary outlook.com account perfectly well.

## What it registers, and why by name

Five delegated Microsoft Graph permissions:

| Permission | Why |
|---|---|
| `offline_access` | Without it the token endpoint returns no refresh token and the mailbox stops working 60–90 minutes later |
| `User.Read` | Read once at link time, for the mailbox's own address |
| `Mail.ReadWrite` | Reading, drafting, moving, deleting, message categories |
| `Mail.Send` | Separate because Graph separates it — which lines up with mailroom splitting `send` from `draft` |
| `MailboxSettings.ReadWrite` | Message rules, automatic replies and the master category list. None of them are covered by `Mail.ReadWrite` |

They are resolved from Graph's service principal **by name**, so a name that does not exist
fails at plan. Written as GUIDs — which is what the portal shows you — a wrong one registers a
permission that is real, wrong, and noticed much later when a mailbox will not do something.

Keep the list in step with `Scopes` in `internal/provider/microsoft/microsoft.go`. That is
what mailroom asks for at consent; this is what the directory will allow. Ask for something
unregistered and consent fails without naming it.

## Two settings that fail late if you get them wrong

Both are why this is worth doing in Terraform rather than clicking through the portal, where
each is accepted at creation and rejected at consent — in front of whoever is trying to link a
mailbox, not in front of you.

**`sign_in_audience` and `MAILROOM_MICROSOFT_TENANT` have to agree.** The default here is
`AzureADandPersonalMicrosoftAccount`, which pairs with mailroom's default of `common`. Choose
`AzureADMyOrg` and you must also set `MAILROOM_MICROSOFT_TENANT` to your tenant id, or consent
fails with `AADSTS50194`.

**Access tokens must be v2.** Entra refuses the personal-account audiences with anything else,
and the default is 1. It is what mailroom wants regardless, since it authorizes against the
v2.0 endpoints. Set here, not something you can forget.

## The client secret

Generated by default, which puts it in Terraform state. That is fine if the state is stored
somewhere you would keep a password and wrong otherwise — `-var create_client_secret=false`
skips it and you create one by hand under **Certificates & secrets** on the registration.

Read it without putting it through a terminal or a shell history:

```sh
terraform output -raw client_secret | <your secret store>
```

Rotation is `terraform apply -replace=azuread_application_password.mailroom`, and it is not
seamless. The old secret is destroyed as the new one is created, so mailroom holds a dead
secret until the new one reaches its environment and it restarts. **Mailboxes already linked
keep working** — their refresh tokens are sealed in mailroom's database and are not reissued
by this client — but no new mailbox can be linked in the gap.

## Personal versus work mailboxes

A personal mailbox — outlook.com, hotmail, live.com — has the full capability surface as far
as anything here has tested. Live conformance against one on 22 August 2026 passed 18 of 19
checks, the one skip being a case that does not apply, and both **message rules** and
**automatic replies** read without error.

An earlier version of this page said Exchange refuses those two on consumer mailboxes with a
403. That came from Microsoft's documentation rather than from a mailbox, and it is not what
happened. What is still untested is *writing* either one on a consumer mailbox: the live
suite is read-mostly by design. If Graph does refuse a write, mailroom reports it as
`unsupported_by_provider` naming the operation.

## Consent looks alarming the first time

An application without publisher verification shows an unverified-publisher notice on the
consent screen. For an instance only you consent to, that is what an unverified app looks
like rather than a sign anything is wrong. Publisher verification requires a Microsoft
Partner Network account and is not worth it for a self-hosted deployment.
